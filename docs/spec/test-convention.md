# テスト規約

## 0. 目的と適用範囲

本規約は `tests/` 配下にテストを追加・変更する際の判断基準を定める。対象はテストの「書き方」であり、テストの実行スコープ運用（どのテストをいつ回すか）は §6 で扱う。

原則は一つに集約される。

> **落ちたときに、実バグまたは本物の契約違反を示すテストだけを書く。**

テストを書く前・レビューする前に、次の3つの問いで判定する。

1. **契約か実装詳細か**: このテストは呼び出し側に約束している振る舞い（契約）を検証しているか。実装の内部構造をなぞっているだけなら、実装変更のたびに書き換わり何も保証しない
2. **壊れ方を言えるか**: 対象がどう壊れたときにこのテストが落ちるか、具体的な壊れ方を1つ挙げられるか。挙げられないテストは検出力を持たない
3. **保証範囲が読めるか**: 何を保証し、何を保証しないかがテスト名と assert から読めるか

## 1. コードテストの規範

既存テストスイートで実際に守られてきた規範の明文化である。新規テストもこれに従う。

1. **実DBで検証する**: サービス層のテストは `temp_db` fixture（実SQLite + 全migration適用）を使う。DBアクセスを内部mockで置き換えない
2. **mockは外部境界に限る**: mock/monkeypatchの対象は、embeddingサーバーHTTP・relay HTTP（`httpx.MockTransport`）・環境変数・時刻・subprocessといった外部境界のみ。テスト対象モジュール内部の関数をmockして「mockが返した値をmockで検証する」自己成就構造を作らない。例外: 呼び出し回数の観測だけを行い実処理は素通しするspyラッパーは内部関数に対しても許容する
3. **エラーは契約として検証する**: エラー応答は `result["error"]["code"]` の完全一致で検証する。「エラーになること」だけの確認で止めない
4. **内容までassertする**: 存在（`is not None`）・件数（`>= 1`）・型（`isinstance`）だけで止めず、値そのものを検証する。範囲チェックで妥当なのは乱数など本質的に非決定的な出力に限る
5. **DB直接SELECTでの検証は許容する**: 永続化の保証にはテーブル直接参照が有効である。テーブル構造も契約の一部とみなす（構造変更時にテストが追従するコストは受け入れる）
6. **リソース契約もテストできる**: N+1回避（バッチ関数が1回だけ呼ばれる）、conn共有（テスト対象が自前で `get_connection()` を呼ばない）などは、spyによる呼び出し回数検証で保証する

### migrationテストの定型

`tests/test_migrations/` のテストは次の型に従う。

1. 対象migration適用**前**の状態確認（テーブル・カラムが存在しないこと）
2. yoyoで対象migrationまでを部分適用
3. 適用**後**の状態確認（テーブル・カラム・インデックス・制約の存在）
4. 適用前に投入した既存データが破壊されていないこと
5. 制約違反が `sqlite3.IntegrityError` で拒否されること

## 2. 文書（SKILL.md / docs）に対するテストの原則

> **文書の文言はテストしない。文書と実装が食い違うと壊れる関係だけを、実装から期待値を導出してテストする。**

SKILL.md は AI が読んで実行する自然言語プロンプトであり、その契約は「AI がそれを読んでどう振る舞うか」である。特定の文字列が本文に存在するかの assert はこの契約を検証できない。さらに文言テストは意図的な文書改善でも落ち、落ちたときにテスト自身は「事故か改善か」を判定できないため、書き換えコストだけが残る。

文書の陳腐化検出は本来 lint / checker の管轄である（`docs/spec/doc-sync-convention.md`）。テストで同じ役割を二重実装しない。

### 許可される2形

- **導出型整合性lint**: 期待値を実装から機械的に導出して文書と突き合わせる。実装と文書という2つの真実源が食い違ったときだけ落ちるため、実害のあるdoc腐敗を検出できる
  - 例: `src/main.py` の `@mcp.tool(` 出現数を数えて `docs/spec/mcp-tools.md` の「全Nツール」表記と照合する
  - 例: `hint_service` の `MARKER_*` 定数を introspection で列挙し、SKILL.md 記載との過不足を両方向で検証する
  - 「全40ツール」のような**固定値の直書きは導出ではない**ため、この形に含まれない（次の正当な変更で落ちるだけの写経になる）
- **構造smoke**: プラグインローダーやフックプロトコルが機械的に要求する構造の検証。SKILL.md の存在、frontmatter の必須フィールド（`name:` 等）など
  - skill 1個ごとに専用テストファイルを作らず、全 SKILL.md を横断する parametrize 1ファイルに集約する

### 禁止される2形

- **PR差分の写経**: そのPRで入れた文言の存在 assert、旧文言の非存在 assert（否定列挙を含む）。§3 の pr-diff-echo 参照
- **文言の固定（tripwire）**: トリガーフレーズ・見出し・手順の順序など、文書内容の存在チェックによる「うっかり変更検知」。この役割は CI の claude-code-review のレビュー観点（SKILL.md description 変更時のトリガー網羅確認）に移管済みであり、テストでは行わない

## 3. アンチパターン集

レビュー時はパターン名で指摘する。各項は「なぜダメか」で定義しており、表記の形式一致ではなく意図で判定する。

| パターン | 内容 | なぜダメか | 適用外 |
|---|---|---|---|
| assertion-weak | `> 0` / `>= 1` / `is not None` / 型チェックのみで内容を検証しない | 実装変更で空・ゼロ・壊れた値が紛れ込んでも検出できない | 本質的に非決定的な出力（乱数等）の範囲検証 |
| docstring-claim-mismatch | docstringが主張する性質とassertが検証する性質の乖離 | テストが保証していると読み手が信じる範囲と実際の保証が食い違う | — |
| no-assertion | assert が無い、または「例外が出なければOK」コメントのみ | 何も検証していない。例外不発を保証したいなら、その旨をテスト名にし正常系の結果をassertする | — |
| implementation-mirror | 内部ヘルパーのmock多用や、対象関数の分岐構造の1:1なぞり | 実装と一緒に書き換わるため契約を保証しない | 外部I/O自体が対象の場合のmock、時間依存処理の構造模写 |
| constant-mirror | チューニング定数・設定値そのものを assert する | 定数を変更したら落ちるだけで、その値がもたらす振る舞いを検証していない | 定数の**由来の同期**を検証する導出型lint（§2） |
| pr-diff-echo | PRで入れた文言の存在＋旧文言の非存在をassertする（「全40ツール」あり・「全39ツール」なし、のような否定列挙を含む） | マージ時点から回帰検出力ゼロ。次の正当な変更で落ち、書き換えられるだけの負債 | — |
| phrase-pinning | 文書の文言・見出し順序の存在チェックで変更を検知する | 事故と改善を区別できず、文書改善を妨げる。§2 参照 | §2 の許可2形 |

## 4. 配置と命名

- `tests/unit/`: in-process で完結するテスト。実DB（temp_db）の使用可
- `tests/integration/`: 複数サービスの連携・MCPツール層の配線を検証するテスト
- `tests/e2e/`: subprocess 起動（hooks・CLIスクリプト・実サーバー）を伴うテスト
- `tests/test_migrations/`: migration の部分適用テスト（§1 の定型）
- `tests/services/`: 歴史的経緯で残っている。新規テストはここに置かず、上記4分類のいずれかに置く（CIでは`unit`ジョブの一部として実行される）
- 命名は対象モジュールに対応させる: `src/services/foo.py` → `tests/unit/test_foo.py`。対応が機械的に辿れることが、実装時の「対応テストだけ回す」運用（§6）の前提になる
- 同名テストファイルを複数ディレクトリに置かない（対応の一意性を壊す）

## 5. 文字数・実行時間バジェットのテスト

上限値の回帰テスト（docstring 1,900字、SessionStart context 予算等）は次の形に従う。

- 新規超過の検出を主 assert とする
- 既知の超過項目は `KNOWN_OVER_BUDGET` として列挙し、`xfail(strict=True)` で追跡する（解消されたらテストが落ちて気付ける）
- 実行時間の assert（例: hook 3秒以内）は実行時間がプロダクト契約である場合のみ許容する。CI環境での揺らぎを見込んだ閾値にする

## 6. 実行スコープの運用

実装フェーズでのテスト実行は「変更ファイルに対応するテスト + 関連する integration テスト」までに絞る。フルスイートの実行は push 後の CI に委譲し、done 条件は「対応テスト + lint 通過」とする。CI の失敗は別ターンで吸収する。

## 7. CIによる形状チェック（`test-pyramid` job）

`.github/workflows/test.yml` の `test-pyramid` job が、本規約の一部を機械的に強制する。

1. `scripts/check_test_dir_coverage.py`: `tests/` 直下の全サブディレクトリが `.github/workflows/*.yml` のいずれかのjobから参照されていることを検証する。参照の無いディレクトリはCIで一切実行されていない可能性が高い
2. `scripts/check_unit_subprocess_placement.py`: `tests/unit/` 配下に実プロセスのsubprocess起動を含むファイルが紛れ込んでいないかを検証する（§4のtests/unit/tests/e2e分類を強制）。既存の許容ファイルは `scripts/test_pyramid_allowlist.txt` に列挙する
3. `scripts/check_test_removal.py`: base commitからhead commitにかけて、気づかれずに消えたテスト関数が無いかを検証する。意図的な削除であれば、PR本文に `[test-removal: <理由>]` 形式のマーカー行を含めることで通過できる（`[no-schema-shape-change]` 等の既存の例外マーカーと同じ運用）

## 8. 本規約の配達経路

- 正本: 本ファイル（`docs/spec/test-convention.md`）
- 書き手向け: `tests/CLAUDE.md` が最重要原則と正本へのポインタを持つ（tests/ 配下のファイル編集時に自動でコンテキストに載る）
- レビュー: `.github/workflows/claude-code-review.yml` のレビュー観点が本規約を参照する
