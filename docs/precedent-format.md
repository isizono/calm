# decision / material 定型節フォーマット仕様

## 0. 読み方

本ドキュメントは decision の reason 本文（および material の content 本文）に書く
定型節規約の正本である。パーサ実装は `src/services/precedent_pure.py` の
`parse_precedent_sections` / `summarize_precedent` であり、両者は常に一致させる。
文法を変更する場合は本ドキュメントとパーサ実装を同時に更新する。

節はすべて任意である。この規約は decision の記入を必須化するものではなく、
書くと構造として読み出し面（`get_decisions` / `get_by_ids` 等）に反映される、という
一方向の恩恵を提供するものである。

## 1. 目的

decision は追記専用であり、本文（reason）が唯一の一次記録である。この規約は
以下の3種類の情報を本文に機械可読な形で残すためのものである。

- **却下案**: この裁定で検討して採らなかった案とその理由。将来のセッションが
  同じ案を再提案する前に読むべき情報。却下案の再挑戦は禁止ではなく、「却下理由の
  前提が崩れたか」の確認を要求する読み方をする。
- **適用条件 / 適用外**: この decision が binding になる文脈の内側と外側。
  誤類推（射程外の判例を適用してしまう誤り）のガードであり、「隣接していて
  混同しそうな文脈」を適用外に書くことが最も価値が高い。
- **検証**: この決定・主張が何に対して実測されたか。検証アンカーが無い decision は
  「決定のみ・実測未確認」を意味する。実装状態（実装済み / 未実装）を decision 本文・
  reason に書かず、検証行の有無と内容から読む側が判定する。

## 2. 書式

reason 本文の末尾に、行頭見出しで始まる節を置く。見出しは以下の4種を正規形とする。

```
<自由記述の理由本文>

却下案:
- <案の要約>: <却下理由>
- <案の要約>: <却下理由>

適用条件:
- <この決定が適用される文脈・前提>

適用外:
- <適用されない文脈。隣接するが別扱いの領域>

検証: <検証手段> / <対象コミットSHA・バージョン・対象物> / <日付 YYYY-MM-DD>
```

### 規則

1. **節見出しは行頭に置き、`:` で終える。** 行頭以外に現れた同語（本文中の言及）は
   パース対象外であり、節として誤検出しない。
2. 却下案・適用条件・適用外は `- ` 始まりの箇条書きを項目とする。却下案の各項目は
   `案: 理由` の2分割を推奨するが、`: `（または `：`）を含まない項目も許容する
   （alternative のみ、reason は空文字として扱う）。
3. 検証行は1行完結を基本とし、複数回検証したら複数行書いてよい。`/` 区切りの
   3フィールド（検証手段 / 対象 / 日付）を推奨するが自由記述も許容する。パーサは
   日付パターン（`YYYY-MM-DD`）と7〜40桁のhex文字列（コミットSHA）をフィールド位置に
   依らず抽出する。
4. 節はどれも任意である。**「該当なし」を書くための空項目・ダミー項目を書いては
   ならない**（却下案が無かった裁定に却下案節は不要）。
5. 実装状態（実装済み / 未実装）を decision 本文・reason に書かない。状態は検証行の
   有無と内容から読む側が判定する。検証行が無い decision は「決定のみ・実測未確認」を
   意味する。
6. 節の置き場は reason とする（decision 本文ではない）。却下・射程・検証は
   「なぜこの決定か」の一部であり、FTS 上も reason は body として索引されるため
   検索面の不利は無い。

## 3. material への適用

検証行（`検証: <手段> / <対象> / <日付>`）は decision の reason 専用ではなく、
**material の content 本文にも同一文法で書いてよい**（検証レポート・実測記録の
material が自身の検証アンカーを機械可読に持てる）。material 側は他の3節
（却下案・適用条件・適用外）を対象としない。パーサは type 非依存にテキストを
受け取るため、material 向けの追加実装は不要である。

## 4. 近似見出し（表記ゆれ）

以下の語は正規の見出しと混同しやすいため、行頭に `:` 付きで現れると節としては
採らず warning を記録する（節見出しと同様の効果は持たない）。

```
却下例, 棄却案, 不採用案, 適用範囲, 対象外, 検証済み, rejected, scope
```

このリストは `src/services/precedent_pure.py` の `NEAR_MISS_HEADERS` が正本である。

## 5. パーサの返り値

`parse_precedent_sections(reason: str) -> dict | None`:

- 正規の見出し・近似見出しのいずれも1つも検出されなければ `None` を返す
  （定型節規約が適用されていない本文との判別に使う）。
- 1つでも検出されれば以下の形の dict を返す:

```python
{
  "rejected_alternatives": [{"alternative": str, "reason": str}, ...],
  "scope_in":  [str, ...],   # 適用条件
  "scope_out": [str, ...],   # 適用外
  "verification_anchors": [
    {"raw": str, "date": str | None, "commit": str | None}, ...
  ],
  "warnings": [str, ...],   # 表記ゆれ・空節・アンカー日付欠落など
}
```

warning はパース失敗を意味しない。パーサは常に best-effort で構造を返し、
気づいた事由を `warnings` に積むだけである。

`summarize_precedent(parsed: dict) -> dict`（`parsed` は `None` でないもの）は
レスポンス添付用のコンパクト形を作る:

```python
{
  "rejected_alternatives": <件数>,
  "scope": <適用条件/適用外のいずれかが非空か bool>,
  "verification_anchors": [<raw 文字列>, ...],   # 生テキストのまま。空リスト=決定のみ
}
```

## 6. 読み出し面への反映

`get_decisions` / `get_by_ids` は、decision の reason に節があれば item に
`precedent`（上記コンパクト形）を追加する。**節が無い decision にはキー自体を
付けない**（legacy 本文と規約準拠本文を区別できるようにするため）。`search()` の
検索結果（snippet ベースの discovery 面）には付与しない。

## 7. 既存データの扱い

一括 backfill は行わない。規約は新規 decision から前向きに適用する。過去の
reason 本文への遡及編集（検証アンカーの事後合成を含む）は一次記録の改竄にあたるため
行わない。頻繁に引かれるのに節が無い decision に遭遇したら、定型節付きの新 decision
で supersede し直す運用を想定する（supersede は正規のライフサイクル操作であり、
旧記録を改変せず系譜として残る）。
