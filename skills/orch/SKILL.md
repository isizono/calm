# orch

## 全体像

orchとは、`orch`タグの付いた未完了のアクティビティで、説明の先頭に「担い手」欄を持つもの。担い手欄に名前とsessionIdで書かれた窓口が、今のorchの担当（今の担い手）である。担い手欄が「空席」、または書かれた窓口が生きていない状態は異常ではない。子として振ったbgは動き続け、報告はログに溜まる。

一生のサイクルは次の順で回る。

1. **なる**: 仕事を受けた窓口が、自分1体で抱えきれないと判断したら、orchになる（同じ範囲のorchが既にあれば、それに合流するか担い手に頼む）
2. **振る**: 子をbgに切り出し、束縛してから起動する
3. **追う**: 子とbgの状態を見る
4. **一覧**: すべてのorchの担い手・bg・子を一望する（朝はこれに加える形で使う）
5. **空ける／世代交代／代わる**: 窓口を閉じるとき、担い手が自分から後継に渡すとき、次に触った窓口が引き継ぐとき
6. **終える**: 子が済んだ、またはユーザーの了承を得て閉じる

orchの担い手は、子になる作業をサブエージェントやWorkflowでも自分でせず、必ずbgに振る。orchが自分でやるのはまとめ役の仕事（振り分け・状態の確認・他セッションとの調整・ユーザーへの取り次ぎ）と、自分の判断のための協議（相談役との協議）だけである。

orchは束ねるだけでなく、担当範囲の成果に責任を負う。判断が要る場面では、ユーザーに聞く前に、相談役との協議と実データの収集（調査・実測はbgに振る）で自分で詰める。相談役とは、判断の材料と案を返すだけの相談専用のサブエージェント（その環境で呼べる設計・推論向けのロール。無ければ、判断の論点と材料を渡して案を求めるサブエージェント）を指す。協議は結論を出すための相談で、調査・実測・実装の作業は含まない。結論と責任はorchが持つ。数セッションまたぐ仕事では、相談役をbg常駐で立てる（[正解の無い仕事を回す](#正解の無い仕事を回す)節。常駐の相談役にも同じ定義を当てはめる）。ユーザーに上げるのは[ユーザーに上げるもの](#ユーザーに上げるもの)の列挙に当たるものだけで、それ以外は在席でも自分で決め、決めた内容と根拠を報告する。

## 発動の範囲

「orchとして進める」「bgに振って」「orchの状況見せて」「○○のorch続けて」「○○のorch終えて」などのユーザー発話のほか、窓口のClaudeが自分1体で抱えきれないと判断した場面でも自発的に発動してよい。`orch`タグの付いたアクティビティにcheck-inしたとき（check-in skill経由か、`check_in`ツールの直接呼び出しかを問わない）は、ユーザーの発話がただの「続きやる」「チェックイン」でも必ず発動し、[代わる](#代わる)節から入る。

窓口が自分1体で抱えきれないと判断する目安は、判断の要る子の目標が2つ以上ある・長く待つ、に加えて、次のどれかに当たるとき。

- スコープが広くなりすぎた
- 複雑すぎて、やるべきことに自信が持てない
- 情報が足りなすぎる
- 文脈のコントロールが1体ではしんどい

正解が外に無く（テストや仕様で合否が決まらない）、1セッションで閉じない仕事も、orchで回す。orchでない窓口は、この種の仕事を`intent:discuss`で起票しない。[正解の無い仕事を回す](#正解の無い仕事を回す)節に従う。

bgに振らずその場で完結する単発の作業やレビューには発動しない。

## なる

### 同じ範囲のorchがあるか確認する

[一覧](#一覧)節の手順でsearchし、同じ範囲のorchが既にあるか確認する。

- 空席なら引き受ける（[代わる](#代わる)節の手順）
- 担い手がいればその窓口に頼む（peer-nudge skill経由）

orchは無いが、同じ範囲を束ねる未完了のまとめ役（`orch`タグも担い手欄も無い「[統合]」など）があるとき、またはユーザーが既存のアクティビティを名指ししてorchにするよう頼んだときは、新しく起票せず、それをorchにする（[既存のまとめ役をorchにする](#既存のまとめ役をorchにする)）。新しく起票すると、同じ範囲に親が2本並ぶ。

### 無ければ起票する

- activity-startを経由せず、`add_activity`を直接呼ぶ（`check_in=True`）。intentは`intent:discuss`
- タグに`orch`を含める。domainや内容を表す素タグも付ける
- 説明の先頭に状態節の雛形を置く（[状態節とgoalの雛形](#状態節とgoalの雛形)節を参照）。担い手欄には自分を書く（`claude agents --json`で`pid`が`$CLAUDE_PID`の行の`name`と`sessionId`を使う）
- 起票と同じ手番で、goalを付ける。形は起点で選ぶ（[状態節とgoalの雛形](#状態節とgoalの雛形)節）
- 最初に振る子が既に分かっているなら、起票のあとすぐに[振る](#振る)へ進み、子を束縛してから開始の宣言を返す
- 同じ手番で[担い手になった手番で仕込むもの](#担い手になった手番で仕込むもの)を仕込む

### 担い手空席の常設orchとして起票する

[recompose-context](../recompose-context/SKILL.md) skillで、束ね役の親の提案にユーザーが了承したときの起票。bgに振る話ではなく、同じテーマの子を束ねるために立てる。

1. [無ければ起票する](#無ければ起票する)と同じに`add_activity`で起票する。担い手欄は「空席」とする。この時点ではgoalを書かない
2. 了承された子を束縛する。根拠はユーザーの了承で、条件の書き方だけ[既存のまとめ役をorchにする](#既存のまとめ役をorchにする)の手順4の末尾の段落に合わせる（子にgoalが無ければ後付けする）
3. 束縛した条件を持つ常設のgoalを書く（[状態節とgoalの雛形](#状態節とgoalの雛形)節。束縛してから書く）
4. [開始の宣言](#開始の宣言)は返さず、立てたorchと結んだ子の題を一言で伝える。担い手が要るときは「○○のorch続けて」で引き受けられる

### 既存のまとめ役をorchにする

1. `get_by_ids`で今のタグと説明を読み、`get_goal`でgoalの`label`を読む。`label`が`closed`（判定済み）なら、そのアクティビティはorchにせず[無ければ起票する](#無ければ起票する)へ進む
2. `update_activity`を1回だけ呼び、説明とタグを同時に書き換える。分けて書くと「タグはあるが担い手欄が無い」途中の状態ができ、[一覧](#一覧)の付け替えがタグを外してしまう
   - 説明: 先頭に状態節を置く（[状態節とgoalの雛形](#状態節とgoalの雛形)節）。担い手欄には自分を書く（名前とsessionIdの取り方は[無ければ起票する](#無ければ起票する)と同じ）。bg表には、報告先がこのアクティビティで生きているbgがあればその行を書き、無ければ「（無し）」とする。約束・預かり・反映待ちは「（無し）」から始める。元の説明は、役割と範囲として状態節の下に残す
   - 元の説明のうち「orchではない」など、orchでないことを前提にした記述は消し、代わりに経緯へ「{日付}にorchにした（それまではorchでないまとめ役）」の1行を残す。雛形の「書かないもの」に当たる記述（他のorchの担当セッション名、運用規約の写し）も消す
   - タグ: 読んだタグを全部含め、`orch`を足し、intentを`intent:discuss`に替える。`update_activity`の`tags`は全置換なので、読んだタグを落とさない
3. 同じ手番で、goalを形に合わせる。形は起点で選ぶ（領域を束ねてきたまとめ役なら常設になるのが普通）
   - `undefined`: 雛形どおり`set_goal`で作る
   - `not_needed`（常駐の不要印）: `set_goal(..., replace=True)`で雛形のgoalに置き換える。不要印のまま残さない
   - `active`: goalは作り直さない。常設にするなら、`update_goal`の`op=add`で錠の条件（担い手human、「ユーザーがこのorchを終えることを了承した」）を足す。期限付きならそのままにする
4. 範囲の中で、まだ束縛していない既存のアクティビティを、下の基準で子にする
5. [担い手になった手番で仕込むもの](#担い手になった手番で仕込むもの)を仕込む
6. [開始の宣言](#開始の宣言)を返す。新しく作らず「[統合] ○○」をorchにしたことを含める

既にある未完了のアクティビティを子にするのは、記録から、このorch（またはorchにする前のまとめ役）の仕事として切り出されたと推せるものに限る（[recompose-context](../recompose-context/SKILL.md) skillの「親への結びつけ」と同じ基準・同じ条件の書き方）。別のorchの子として束縛済みのもの（各orchの`get_goal`の条件の`bound`に出るもの）は子にしない。別の窓口が作業中のものも、基準に合えば束縛してよい。束縛しても作業する窓口は変わらない。子にgoalが無ければ、束縛するときに後付けする（書き方はrecompose-context skillの「goalが未定義」と同じ）。goalが無いままだと、束縛した条件「子のgoalがachievedで閉じた」を満たせない。

### 開始の宣言

起票（または既存のまとめ役をorchにする手順）が済んだら、次を含む一言をユーザーに返す。

- orchとして回すこと
- 形（期限付き／常設）
- 戻ってくるもの（PRのマージ、判断が要るときのask、止められた操作の許可）

見本:「これは子が3本に分かれて判断も要るので、bgに振って私がorchとして回すね。『[統合] ○○』を作った。形は期限付きで、子が全部済んだら閉じる（ずっと持つ常設にしたければ言って）。あなたに戻ってくるのは、PRのマージと、判断が要るときのask。止められた操作の許可が要るときは、まとめて頼む」

## 振る

### 数える

振る前に、`claude agents --json`で全セッションの生きたbg（`kind=background`かつ`pid`あり）を数える。ユーザーとの取り決めの上限を超えるなら、超えない範囲まで待つ。

### 束縛して起動する

子1本につき、次の3段を同じ手番で続けて行う。

1. `add_activity`を`check_in=False`で呼び、子を作る（`orch`タグは付けない。このタグはorchアクティビティ自体にだけ付ける）
2. 子に`set_goal`でgoalを作る
3. orchのgoalに`update_goal`（`op=add`）で、子のアクティビティへ束縛した条件を足す

続けて依頼文ラッパー（`${CLAUDE_PLUGIN_ROOT}/scripts/bg_dispatch.py`。必須引数は`--activity-id`・`--activity-title`・`--worktree`・`--parent-goal-handle`・`--parent-condition-id`）で起動する。親goalの指定を必須にする（orchの子は依頼文ラッパーで親goalを指定して振る）。起動後、`waitingFor`を1回見て、起動の入口で止まっていないか確かめる。起動できたら状態節のbg表に1行足す。

期限付きのorchにも、最初の子と範囲の違う子を後から足してよい。2本目のbgのために2本目のorchを作らない。

起動後のbgに、起動時の範囲の外の仕事を送らない。範囲外の残件は新しい子として振る。

### 起動形

信頼済みのディレクトリで、作業ツリーの中から起動する。止まったら`waitingFor`を見る。zshのクォート・特殊文字のエスケープに注意する。リポジトリ別の起動場所の具体は、環境ごとの私的な取り決めに従う。

## 依頼文の書き方

依頼文ラッパーが生成する依頼文に、次を含める。

- **報告先**: 親のorchアクティビティ。bgは報告を常にそのアクティビティへ`add_logs`で書く
- **越えない線**: 外向きの操作（他人のブランチ・外部サービスへの書き込み）、`~/.claude`配下の変更、既決を見直すことになる判断、auto modeや権限に止められた操作は、進めずに報告先へ返す。止められたら迂回しない
- **待たずに進む範囲**: 上の線の内側の実装上の判断は、確認が要る場面でも待たずに最も妥当な方針で進め、判断をPR本文と報告に書く
- **人間宛てのaskを起票しない**: 人の判断が要るときは報告先へ返す
- **EnterWorktreeは使わない**
- **マイグレーション番号**: 必要になったら、origin/mainとopen PRの番号の最大値+1を取り、報告先へ宣言する。返事は待たずに進む。兄弟のbgが同じ番号を取ることはありうるが、yoyoは番号が同じでもファイル名が違えば別のmigrationとして扱い、適用順は`-- depends:`で決まるので、衝突しても壊れはしない。番号を直すのは後からマージするPR（後発側はマージ順で決める）で、マージする者（orch）が[マージ前](#ユーザーに上げるもの)にorigin/mainと突き合わせ、重なっていれば次の空き番号に振り直させる
- **兄弟との連携**: 兄弟（同じ親goalに束縛された他の子）の担当に関わる事実（共有ファイル・マイグレーション番号・mainの破損・前提の変化）を見つけたら、報告先に加えて、その兄弟へもSendMessageで知らせる義務。兄弟の一覧は依頼文に埋め込まず、受けたbgが親goalのconditionsとget_sessionsから引く（orchは子を順に振るので、起動時点では後から振る兄弟が決まっていない）。送るのはこの周知だけで、作業の依頼・質問・進捗は送らせない
- **止める前の`sync-memory --minimal`**: 最後の報告の前に実行する
- **相談先**: 相談役がいるときは、作業役の依頼文に`--consultant-activity-id`で相談役を相談先として名指しする（兄弟ではなく、SendMessageでの相談を許す）。相談役自身の依頼文は`--role consultant`で作り、`--holder-name`・`--holder-session-id`・`--holder-transcript`で起動時点の担い手を渡す（相談役の依頼文には、担い手の見張りが常設の仕事として入る。[担い手になった手番で仕込むもの](#担い手になった手番で仕込むもの)の2）
- 禁止は狭く書き、方針でなく「説明と決定事項に従う」ことを書く。依頼文に`"ultracode"`やWorkflowの実行指示を書かない（[やってはいけないこと](#やってはいけないこと)節）

## 追う

生死の規則は2本ある。

- **bgの生死**: `claude agents --json`で`kind=background`かつ`pid`あり。`state`は生死を表さない
- **窓口（担い手）の生死**: `claude agents --json`で、担い手欄の`sessionId`が一致し`pid`がある行がある（`kind`は問わない）。名前は判定に使わない。Remote Controlの窓口やbgは起動後に名前が自動で変わるため、名前の一致を求めると生きている担い手を死んでいると読んでしまう。そのような行が複数あれば（`/resume`後に並ぶことがある）`startedAt`が最も新しい行を担い手とする（`/resume`すると同じ`sessionId`の行が増え、新しく開いた側が今使われている窓口になるため。両方に`pid`があっても新しい側に送る）
- **担い手への知らせの宛先**: 上で選んだ行の今の`name`。担い手欄に書かれた名前は人が読むための表示で、宛先には使わない

許可待ちは`waitingFor`が`permission prompt`のときと見分ける。`attention`の「止まっている」は見に行く候補で、CI待ち・許可待ち・単純に止まった・まだ振っていない、を上の規則で見分ける。

goalの`children`の「達成」は外した子（waived）を含む。内訳は`get_goal`の条件で読む。次の一手の規則11が束縛した子について「進める」と返したら、orchでは「振る、または振った子の様子を見る」と読む。

報告済みで次の指示を待っているbgは、要らなければ`sync-memory --minimal`を済ませていることを確かめて止める。

## 正解の無い仕事を回す

正解が外に無く、数セッションまたぐ仕事の進め方。人に返すのは、結果と自分で決めたことと[返す3項目](#ユーザーに上げるもの)だけにし、進む向きは相談役との協議で確かめる。

### 問いを立てる

- 仕組みの追記・PR・手順書といった手段に入る前に、この仕事の問いを1文で立てる。goalのstatementと条件は、問いと観測できる状態で書く。成果物ができたこと（「mainに入った」「資料ができた」）を条件にしない
- 立てた問いは、相談役と検査する。次を自分から問う。ユーザーの指摘だけを手がかりにしない
  - その問いは本当に正しいか
  - もっと根本のところに問題はないか
  - 背後にあるシステムの構造は何か
  - もっと単純で明快な解が既にないか
  - ユーザーも自分も持ち込んでいない視点は何か（費用、効いているかの測り方、同じモデルばかりの盲点など）

### goalの形

- orchの常設goalは、子への束縛と錠だけを持つ
- 目的1本につき「目的の子」を1本立てる。goalのstatementは目的（誰がどういう状態か。成果物で書かない）、条件は観測条件（claude）と受け入れ条件（human、1本）
- 時間で確かめる条件（「二度と起きない」など）は「観測用の子」のgoalにexternalで置く。目的のgoalに入れると、achievedが期間明けまで通らない
- 外から観測できる条件を最低1本置く。Claude自身の評価や、成果物ができたことだけを条件にしない。観測条件が書けないなら目的が抽象すぎるので、目的を置き直す
- 目的は「誰が、どういう状態か」で書き、採らなかった読みを2〜3個、やらないことを残す。確認は取らず宣言する（在席ならチャットに1行、不在なら朝の一覧に1行。返事は待たない）。既決の正当化を覆す転換だけは人に返す

### 現状を確かめる

目的を置いたら、手を打つ前に次を見る。結果は現在地節に書く。目的の子のgoalは振る前に作る決まりなので、仮の条件で作って振り、作業役の確認の結果で`update_goal`して直す。

| 見るもの | 見方 |
|---|---|
| 被害 | 障害対応のとき。誰が・どれだけ・今も続いているか・広がっているか。続いているなら応急処置が先 |
| 応急処置 | 障害対応のとき。可逆で内部の手当てなら打つ。本番・外向きなら、推奨と根拠を揃えて1回で上げる。不要なら理由を書く |
| 止まる要因と再開の仕掛け | 5時間のセッション上限、CI待ち、人の返事待ち、auto modeに止められる操作。起こし直しと外からの見張りは、担い手になった手番で仕込んである（[担い手になった手番で仕込むもの](#担い手になった手番で仕込むもの)）。仕込みが状態節に無ければ、ここで仕込む |
| 使う機能が今動いているか | CALMサーバー、searchのdegraded、宛先候補（`CALM_PEER_NUDGE_ENABLED`）、bgの本数の上限、必要な記録へのアクセス。欠けたものは代わりの経路を決め、到達できない記録は「人しか持たない事実」の候補にする |
| 止められそうな操作 | どのタスクでも最初に洗い出す。設定・CLAUDE.md・auto-memoryの編集、bgの起動、他のセッションの停止、外向きの操作など、auto modeに止められそうなものを作業の途中で拾うと止まる。まとめてユーザーに許可を頼み、`autoMode.allow`に入れてもらう（Claudeがsettings.jsonを書くと拒否されるので、文案を渡してユーザーに`/permissions`で入れてもらう） |
| 既にあるもの | 同じ目的の既決・ask・過去の試み（search）。答えがあれば従う |

担い手は調査・実測をしないので、見る主体を分ける。環境側（止まる要因、bgの本数、CALMの状態、宛先候補のON/OFF）は窓口が見る。対象側（被害、応急処置の候補）は作業役が最初の手として見る。現状によって条件が最初から満たされていることもある。

### 相談役の運用

- **立てる時点**: 窓口が、目的を置く前に立てる（bgを立てられるのは窓口だけ）
- **形**:
  - bg常駐（既定）: 数セッションまたぐ仕事なら最初から。経緯を持ち続け、主担当のセッションが変わっても同じ相手と協議できる
  - 都度のサブエージェント: 1セッションで閉じる仕事、またはbgの本数の上限に当たっているとき
  - 経緯を渡さない新しいサブエージェント: 受け入れ判定の前の検査と、途中で目的を見直すときの検査。常駐の相談役は経緯を見ていて作った側の正当化に引きずられうるので、過程を見ていない目を使う
- **役割分担**: 主担当（orchの窓口）は目的・結論・責任を持ち、手を打ち、記録し、人と話す。相談役は実装も調査もしない。ただし担い手の予告止まりの検知だけは、常設の仕事として相談役が行う（依頼文に入っている）。生死・固まりの検知と担い手の文脈の測定・「交代せよ」の送信は観測役が行う（[担い手になった手番で仕込むもの](#担い手になった手番で仕込むもの)の2）。意見が割れたら主担当が決める。往復が1回で済まないなら掲示板で議論を立てる
- **束縛**: 相談役の子のgoalは、claude条件「orchを終える前に相談役を止めた」の1本にする。相談役には終わりが無く、不要印では束縛条件を満たせないため。この条件は[終える](#終える)で扱いが変わる
- **渡すもの**: 目的節と現在地節、次の手と「何を期待してその手を打つか」の1行、手の結果
- **返させるもの**: その手・結果が目的に近づいたか（外部の観測、反証を試みて生き残った仮説、未確定事項の減少のどれに当たるか）とその根拠、見落としや別の読み、方向を変える数字の検算の要否とやり方、人に出そうとしている問いが返す3項目に当たるか
- **協議する時点**（毎手ではなく次の5つ）:
  1. 目的を置いたとき（読み違いの検査）
  2. 現状確認の後、手を決めるとき
  3. 手の結果が出たとき（作業役の報告時）
  4. 人に問いを出す前
  5. 受け入れ判定の前（経緯を渡さない新しいサブエージェントで行う）
- 作業役が直接相談できるよう、依頼文で相談役を相談先として名指しする（[依頼文の書き方](#依頼文の書き方)）。依頼文で配線した辺でしか協力は起きない

### 訂正は届く置き場へ

人に直されたら、その場で直すだけで終わらせない。[remember](../remember/SKILL.md) skillで、次のセッションに届く置き場（エントリ・skill・rules）に書く。成果物（未マージのPRや手順書）の中に直しを入れただけでは、教訓は次に届かない。手当てとして作ったのがセッションの中の仕掛け（cron・購読・SendMessageでの依頼）だけなら、それも次には届かない（remember skillの前処理2）。

### 3機能が効く場面

- **協力機構（宛先候補・peer-nudge）**: 相談役・作業役・近い範囲の別セッションと、その場で1往復で済むやり取りをするとき。話しかける前に`get_sessions`で担当を確かめる
- **掲示板**: 相手が今生きていない、または往復が1回で済まない意見募集のときだけ、boardトピックと[議論]アクティビティ・goalを立てる（board skill）。例は、相談役が上限やプロセス断で生きていない間に意見が要るとき、主担当と相談役または近い範囲の別orchと1往復で収束しないとき。相手が生きていて1往復で済むならpeer-nudgeか[隣のorchへの検査](#隣のorchへの検査)を使う。協議の記録は報告先のorchアクティビティのログに、結論は議論本体のトピックの決定事項に書く
- **フィードバック**: 相談役の指摘が「同じ型の誤り」（書き込み経路の数え漏れ、確認過多など）だったとき、主担当がエントリにして、次に同じ操作をする瞬間に自分へ配達させる

### 受け入れ判定と次の目的

- **渡す**: 説明の先頭に目的節と現在地節を上書きで置く（[状態節とgoalの雛形](#状態節とgoalの雛形)）。次のセッションは目的節を最初に読み、「Claudeが決めたこと」を見直す条件なしに開き直さない
- **受け入れ判定にかける時点**: 目的のgoalのclaude条件が全部終端したとき。報告を出す前に、経緯を見ていない新しいサブエージェントに目的と結果だけを渡して検査させる
- **報告**（資材、1画面）: 目的と採らなかった読み、条件ごとの結果と人が自分で確かめる手段、Claudeが決めたこと上位5件、分かっていないこと、次の目的
- **問い**: 3択（受け入れる／目的が違う／決めたことのN番が違う）。在席ならチャットで聞いて決定事項にし、不在ならaskにしてhuman条件に束縛する（型は[ask-compose](../ask-compose/SKILL.md)）
- **次の目的**: 源は、観測用の子の観測、1段上の目的のうち満たされていない部分、「やらないこと」に置いた隣接問題。受け入れた目的から導けて親を書けるものは自分で立てて新しい子にする。導けない、または費用が大きいものは上げる。終わりは常設orchの錠が人に残す

## 一覧

1. `search(keyword="orch", tags=["orch"], entity_type="activity")`で引き、`get_by_ids`で状態と説明を読んで未完了だけを残す
2. 説明の先頭に担い手欄が無いものはorchとして扱わない。`orch`はorchの目印専用のタグなので、その場で外し、内容に合う素タグに付け替える。CALMのorchの運用を話題にしているものは`orchestration`、別の意味（プロダクトの部品名など）なら、その意味が分かる別の語（例: プロダクト名を前に付けた語）にする。別の語は、先に`search_tags`で近い既存のタグを探し、あればそれを使う。`update_activity`の`tags`は全置換なので、今のタグを読んでから渡す。付け替えはユーザーに確かめず、他の窓口のアクティビティでも行い、付け替えたことを一覧に1行添える。orchにしたいまとめ役だったなら、[既存のまとめ役をorchにする](#既存のまとめ役をorchにする)の手順で付け直す
3. `claude agents --json`で、担い手欄の`sessionId`が一致し`pid`がある行があるかを見る（生死の見方は[追う](#追う)節の窓口の生死の規則による）
4. 各orchの`get_goal`の`children`と状態節のbg表を添える

「各orchに○○して」と頼まれたら、この一覧の生きた担い手（その行の今の`name`）を宛先にし（担当確認・作業依頼はpeer-nudge skill経由）、空席のorchにはログを書く。

### 朝の一覧

「おはよう、どうなった？」のような呼びかけに対し、上の一覧に次を添える。

- マージできるPR（CI・bot指摘の状態、順序の制約つき）
- 止まっているbg（いつから）
- askの件数（`get_overview`の`awaiting_human`から）
- 空席のorchの後始末（担い手欄の更新後に溜まったログの件数、Claudeの条件が出揃ったorch、マージ済みで判定待ちの子）
- 期限付きで閉じたorch
- 受け入れ判定待ちの目的の子（報告の場所）
- 新しく置いた目的（宣言のみで返事は待っていない）
- マージ後にユーザーがやること（状態節の反映待ちから作る）

## 空ける

ユーザーが窓口を閉じると言ったとき（「閉じるから」「終わるから残して」など）に行う。

- 状態節を最新にし、担い手欄を「空席」にする。後任は決めない
- 生きているbgは止めずに残してよい（bg側が最後の報告の前に`sync-memory --minimal`を済ませている）
- ユーザーに「このorchは空席にした。続けるときはどの窓口でも『○○のorch続けて』」と一言伝える

sync-memoryを実行する窓口が、このorchの担い手で、ユーザーが窓口を閉じると言っているときは、sync-memoryの前に先に「空ける」を行う。閉じないsync-memory（途中の記録）では空けない。

## 世代交代

担い手は、次のどれかに当たったら交代に入る。測るのは本人でなく相手側（観測役が担い手を測る）。

- 最後のassistantのusageで、input_tokens・cache_read_input_tokens・cache_creation_input_tokensの合計が33万を超えた（準備に入る線。ここでsync-memoryを始め、38万に届く前に交代を済ませる）
- 圧縮が1回でもあった
- セッション開始後にskills/orchが変わった（観測役には当たらない。skill本文の変更は呼び直しで足りるかを実測中）

観測役が担い手を測り、超えていたら「交代せよ」を送る（[担い手になった手番で仕込むもの](#担い手になった手番で仕込むもの)の2）。担い手が自分で判断して交代しない。担い手と相談役を同時に交代しない（担い手→相談役の順で、間を空ける）。

置き場は決定「orchはtmux -L orchの1画面に置き、交代はペインの入れ替えで」に従う。`tmux -L orch`のセッションorch、orchごとにwindowを1つ、中央を担い手のペインにする。tmuxはシェル関数`t(){ tmux -L orch "$@"; }`で打つ（変数に入れるとzshで単語分割されない）。

ユーザーに窓口を開かせたり「続けて」と言わせたりしない。交代は担い手と後継だけで完結させる。iTerm2の新しい窓は開かない。

1. 状態節（担い手・bg表・約束・預かり・反映待ち）と、あれば目的節・現在地節を上書きで最新にする。自分宛てに届く予定の報告（走っているサブエージェントやbg）は、届く先が無くなるので、待つか、報告先をCALMのログに変えるよう伝える
2. sync-memoryを標準形で実行する（訂正の拾い直しを含む）
3. 旧担い手が、中央ペインを一時的に割り（`split-window`）、そのペインに`send-keys`で後継を起こす。コマンドは `cd ~/workspace && python3 <labの絶対パス>/scripts/pane_claude.py --role holder <自分と同じ起動フラグ> '<orchの題>のorch続けて。旧担い手は<名前>（sessionId <id>）。最初の手で、orchアクティビティ（id <orchアクティビティのid>）の説明の全文をget_by_idsで取り、「担い手: 」で始まる行だけを、自分の名前・sessionId・今の時刻で「担い手: 名前（sessionId 値）／時刻」の形に置き換え、update_activityで説明を書き戻す（名前とsessionIdはclaude agents --jsonでpidが$CLAUDE_PIDの行から取る）。他の行は読まずにそのまま残す。次に、check_inより前に、根の答えの掲示板「<掲示板の題>」の最新の版の要点節（3,000字まで）だけを読み、壊れる場面を1つ掲示板に書いてから代わる。題は「条文<番号> / <場面の主語>: <壊れる場面の要約>」の形にする。版はsearch（keyword「根の答え」、tags=["board","root-answer"]、entity_type=log）の結果から作成時刻が最も新しい1本を選びget_by_idsで読む。書き終えるまで、check_in・get_logs・orchの説明の他の行と掲示板の他の投稿は読まない'`。「次に、check_inより前に」以降は、orchが根の答えの掲示板（今の答えの版を投稿で重ねるboardトピック）を持つときだけ付ける。後継はorch skillを読む前にこの段を踏むので、担い手欄の書き方と版の読み方は起動の文に書き切る（後継の手順は[代わる](#代わる)の1と2と同じ）。自分の起動フラグは`ps -o args= -p $CLAUDE_PID`で読んで同じものを渡す（`--plugin-dir <labの絶対パス>`を含める。落とすとlabの仕組みを持たずに生まれる）。`claude`を直接打たず、ラッパー`pane_claude.py`を通す。ラッパーは担い手以外の返事待ちの自動askを切り、tmuxサーバーから継承されるCLAUDE_CODE_SESSION_IDを外す
4. 旧担い手は、5分以内に`claude agents --json`に新しいinteractiveの行が出て担い手欄が書き換わるのを見届ける。書き換わらなければ担い手を続け、朝の一覧に載せる。再試行は1回まで
5. 後継は次の順で行う: [代わる](#代わる)の手順で、担い手欄だけを自分に書き換え→版の要点節を読んで掲示板に壊れる場面を書き→`check_in`→状態節の更新時刻以降のログを読み→[担い手になった手番で仕込むもの](#担い手になった手番で仕込むもの)を仕込む→観測役・相談役へ「担い手が代わった（名前・sessionId）」をSendMessageで知らせる→旧担い手を止める（`kill -TERM <pid>`）→`swap-pane`で自分を中央に入れ、旧ペインを`kill-pane`し、タイトルを付け直す
   - 旧担い手がtmuxの外（iTerm2の普通のタブ）にいたときだけ: 止める前に`ps -o tty= -p <pid>`でttyを控え、止めた後に残るのがlogin・zshだけなのを`ps -t <tty>`で確かめ、osascriptでiTerm2のsessionsからtty一致の1つだけを`close`する
   - 止めるのが拒否されたら、旧担い手が担い手欄の書き換わりを確かめて自分で止まる。それも拒否されたらidleのまま残し（害は無い）、後継が朝の一覧の「あなたがやること」に「旧窓口<名前>を閉じる」を載せる
6. 旧担い手は、後継が担い手欄を書き換えたことを確かめる前に自分から閉じない。後継からの知らせを受けたら、残す報告が無いことを返して待つ（止めるのは後継）

作業役の確認は`claude -p`で行い、窓もペインも開かない。無人の起点から後継を起こすことは、環境の限界として範囲外（[担い手になった手番で仕込むもの](#担い手になった手番で仕込むもの)の2の見張りも、検知して報告するところまで）。

### 担い手がbgのとき

bgの担い手は子のbgを立てられない。子を振る必要が出たら、担い手が生きている窓口から後継を起こしてもらうか、朝の一覧に載せる。人に返す問いは画面でなくaskにする（bgの画面はユーザーに見えない）。

## 代わる

次にこのorchに触った窓口が行う。最初の手は担い手欄の書き換えで、攻撃も`check_in`もその後にする（交代中に届いた人の答えの拾い手を途切れさせないため）。

1. 担い手欄だけを自分に書き換える。`claude agents --json`で`pid`が`$CLAUDE_PID`の行の`name`と`sessionId`を取り、orchアクティビティの説明の全文を`get_by_ids`で取って、「担い手: 」で始まる行だけを「担い手: {名前}（sessionId {sessionId}）／{今の時刻}」に置き換え、`update_activity`で説明を書き戻す。置き換える前の行にあった更新時刻は控える（4で使う）。他の行は読まずにそのまま残す。担い手欄の1行だけは、2の攻撃を書く前に触ってよい（書くのは1行で、読むのは版の要点節だけなので、新しい目は保たれる）。担い手欄は、以前の値にかかわらず無条件で今の自分の値に書き直す（`/resume`ではsessionIdが同じまま名前とpidだけが変わるので、sessionIdが一致していても書き直しを省かない）
2. orchが根の答えの掲示板を持つなら、`check_in`より前に、壊れる場面を1つ掲示板に書く。状態節（orchアクティビティの説明）の担い手欄以外と掲示板の他の投稿は、書き終えるまで読まない（先に読むと、既に付いた攻撃と同じ所を突いたのかを新しい目として数えられない）
   - 掲示板は起動の文の題で引く。題が無い（手で代わった、観測役のDEAD・STUCKの報告を見て代わった）ときは、orchの題をキーワードに素タグ`board`のトピックを`search`し、説明にそのorchの題がある掲示板を使う。見つからなければこの手順を飛ばす
   - 版は`search`（keyword「根の答え」、tags=["board","root-answer"]、entity_type=log）の結果から作成時刻が最も新しい1本を選び（並び順は関連度なので先頭を取らない）、`get_by_ids`で読む。`check_in`・`get_logs`は状態節やtag notesまで返すので使わない
   - 版（根の今の答え）を書く者は、そのログに素タグ`root-answer`を付ける。後継はこのタグで版を引く
   - 読むのは版の要点節だけで、3,000字まで。要点節が無ければ根と条文の節を先頭から3,000字まで
   - 掲示板トピックへ`add_logs`で書く。題は「条文<番号> / <場面の主語>: <壊れる場面の要約>」の形にする。条文番号は版の条文の番号（番号が無ければ部品の記号）、場面の主語は「どの個体が何をしたとき」
3. `check_in`する
4. 1で控えた更新時刻以降のログ（空席中のbgの報告を含む）を読む
5. `claude agents --json`でbgの生死を見直し、報告済みで次の指示を待つbgのうち要らないものを止める
6. [担い手になった手番で仕込むもの](#担い手になった手番で仕込むもの)を仕込む
7. 世代交代の後継として起こされた（起動の文に旧担い手の名前とsessionIdがある）なら、[世代交代](#世代交代)の手順5で旧担い手を止める

bgへ報告先の変更を伝える手順は要らない（bgは報告のたびに担い手欄を読んで宛先を引くため）。

orch同士の約束・待ちは、宛先を相手のorchアクティビティの題で書き、送る時点で相手の担い手を引く。相手が生きていれば（[追う](#追う)節の窓口の生死の規則）、担当確認や作業依頼はpeer-nudge skillを通して、その行の今の`name`へSendMessageする。空席なら相手のアクティビティにログを書く。

### 担い手になった手番で仕込むもの

担い手になった窓口（[なる](#なる)で起票した、orchにした、または代わった）は、その手番で次の3つを仕込む。どれもセッションの中にしか残らないので、担い手が替わるたびに新しい担い手が仕込み直す。仕込んだことは状態節に1行書く。

1. **自分の定期の起こし直し**: CronCreate（recurring、30分ごと、:00と:30は避ける）。中身は「状態節・現在地節を読み、予告して打っていない手があれば打つ／bgとペインのセッションの生死を見る／相談役の文脈の大きさを測り、[世代交代](#世代交代)の契機を超えていたら相談役を立て直す（新しい相談役に務めを引き継がせてから、旧相談役をclaude stop）／未読の子の報告を読む／orchにcheck_inした応答の`control.unlearned_corrections`に`same_type_pending`があれば、`${CLAUDE_PLUGIN_ROOT}/scripts/corrections.py context`で各件の訂正の前後を切り出し、経緯を渡さずにAgent（thinker）へ切り出しと訂正だけを渡して同じ型の他の誤りを洗わせ、結果を素タグ`same-type-checked`の資材にしてそれらの件と結ぶ／変化が無ければ何も書かずに終える」
2. **外からの見張り**: 常駐の観測役が、担い手の生死・固まり（判定スクリプト`${CLAUDE_PLUGIN_ROOT}/scripts/orch_liveness.py --session-id <sessionId>`のDEAD・STUCK。pidが無い、またはbusyのままtranscriptが25分以上更新されない）と、担い手の文脈・圧縮・skillの版（判定スクリプト`${CLAUDE_PLUGIN_ROOT}/scripts/handoff_trigger.py --session-id <sessionId> --role holder`の`trigger`）を測る。測るだけで判断はしない。`trigger`がtrueなら、観測役が担い手へSendMessageで「交代せよ」を送る（同じ相手に二重に送らない）。DEAD・STUCKなら、観測役がorchのログに書いたうえで、[世代交代](#世代交代)の手順3の形で後継を起こす（1つのorchにつき1時間に1回まで）。この見張りは観測役の依頼文に常設の仕事として入っているので、担い手は観測役がいるかを確かめ、いなければ`bg_dispatch.py --role observer`で自分の名前・sessionId・transcriptのパス（`~/.claude/projects/*/<sessionId>.jsonl`）を渡して立てる。観測役は見るたびに担い手欄から担い手を読み直すので、代わった担い手が頼み直す必要は無い。予告止まりの検知（idleの知らせのたびの、予告した手が打たれずに止まっていないかの検査）だけは相談役に残る
3. **ターンの終え方**: ターンを終えるときは、人宛てのask・`notify_when_idle`の購読・後継のどれかを置いてから終える。報告して「次にやること」を並べて区切らない

1と2の後継・観測役の起動を無人の起点から行うには、ユーザーがその操作をauto modeで許可している必要がある。CronCreateや起動が止められたら、迂回も言い換えての再試行もせず、起動を外した中身（検知してorchのログに書くだけ）で続け、止められたことを状態節とorchのログに書く。そのときは、担い手のプロセスごと落ちても後継は起きないので、観測役の書いたログが次にこのorchに触った窓口への手がかりになる。

## 終える

### 常設・期限付きの終わり方

- **常設**: Claudeの条件（子の条件）が全部終端したら、担い手が1回だけ「このorchを終えてよいか」を聞く
  - 在席ならその場で聞き、答えで錠をsatisfiedにするか、続ける範囲を子にする
  - 不在・空席ならaskを起票し、`update_goal`の`op edit`で錠の条件のboundをaskにする。問い文に答え方を書く（「終えてよければ『終えてよい』。続けるなら追加の範囲を書く」）
  - 答えが「続ける」なら、同じ`update_goal`の呼び出しで、`op edit`で錠のboundをnullに戻し、`op set`（`state=open`、`note`に日付）を送る。追加の範囲を子にして束縛する
  - 束縛先askが回答済みで規則10（束縛先は済んでいる）が出たら、`satisfied`にする前に回答の中身を読む。「続ける」ならsatisfiedにせず束縛を外す（`orch`タグのnotesにも同じ読み方がある）
  - ユーザーの「終わったってことだよね？」のような疑問の形の発話も終える確認の合図として受け取り、1ターンで「終えてよいか」を確かめる
- **期限付き**: 子が全部済めば判定待ちになる。ユーザーの確認を経ずに閉じる前の始末へ進み、閉じたことを一言伝える

相談役の子の条件（「orchを終える前に相談役を止めた」）は、上の「Claudeの条件が全部終端したら」「子が全部済めば」の判定の対象に数えない。相談役は閉じる前の始末で止めるまで終端しないため、数えると判定が永久に出ない。

### 閉じる前の始末

1. openの子ごとに行き先を決める。別のorchに渡すなら渡す先のgoalに束縛を足してから、こちらの条件を理由付きでwaivedにする。やめるなら理由付きでwaivedにし、子を閉じる
2. 生きているbgは`sync-memory --minimal`を指示してから止める。相談役のbgもここで止め、止めたら相談役の子の条件をsatisfiedにする
3. 預かりは別のorchの預かりに移すか、アクティビティかaskにする
4. 反映待ちが残っていれば、朝の一覧の「あなたがやること」に出すか済んだことを確かめる
5. `judge_goal`で閉じる。ユーザーが終えてよいと明言したときは判定の主体を人間（`judged_by="human"`）にする。閉じたことを、在席ならその場で、不在なら朝の一覧で一言伝える

子を閉じる最後の一手（マージを確かめて人間の条件を満たし、子のgoalを判定する）は、その子を束縛するorchの担い手が持つ。マージした窓口が担い手でなければ、担い手へ知らせる。担い手が空席なら、マージした窓口がその一手だけを済ませ、orchのログに書く（代わらない）。

作業ツリーは子の持ち物とし、子を閉じるときにその子を束縛するorchの担い手が消す。auto modeに止められたらまとめてユーザーに頼む。

activity-finishでこのアクティビティを閉じようとしたら、ここ（「終える」）へ進む。

## 隣のorchへの検査

orch自身が設計の決定事項を`add_decisions`で記録する前に、隣のorchへ1回だけ検査を頼む。自分の文脈では見えない既決との衝突・前提の抜けを、別の文脈から指摘してもらうため。

1. [一覧](#一覧)節の手順で、担当範囲が近い別のorch（domainと素タグが重なるもの）を1つ選ぶ。生きているかは[追う](#追う)節の窓口の生死の規則で見る
2. 生きていれば、決定事項の案とその根拠を添え、「既決との衝突や前提の抜けがないか見てほしい」とpeer-nudge skill経由でSendMessageする。検査は1回だけで、返事への再検査は頼まない
3. 返事が来るまで、そのdecisionの記録は保留する。他の作業は続け、次の手番までに返らなければ、検査なしで記録し、記録の本文に「検査を頼んだが返答なし」と書く
4. 返事の指摘を判断して、案を直すか、そのまま記録する。指摘を採らないときは理由を記録に書く
5. 空席、または宛先に送れないときは、検査を省いて記録する

ユーザーとの合意で決まる決定事項や、実装上の判断には使わない。

## ユーザーに上げるもの

次はユーザーに上げる。それ以外は、在席でもorchの中で相談役との協議と実データの収集で判断して進め、決めた内容と根拠を報告する。

- PRのマージ（1本ずつ名指し。マージの前にclaude botの指摘を確かめ、マイグレーションを足すPRはorigin/mainと番号を突き合わせて、重なっていれば振り直させる）
- auto modeに止められる外向きの操作
- 大きな手間や費用（取り決めたbgの本数の上限を超えることを含む）
- ユーザー設定の変更
- ブランチの削除
- 既決のreasonがユーザーの意図に基づくものの見直し
- 人しか持たない事実（Claudeが到達できない記録・事情・記憶）
- 本人の価値判断（目的と記録から導けず、成果物が大きく変わり、覆すと高くつくもの）

判定の問いは「人はどの情報から答えるか」。Claudeが読める情報から答えるなら、Claudeが答える。人に出す前に、相談役にこの分類を通す。同じ問いは2回聞かない。2回目はおすすめで決め、「Claude裁定」と見直す条件を付けて決定事項にする（権限や費用の問いはおすすめで決めず、依存しない進め方に組み替える）。聞いても待たず、仮置きで進む。

skill・docsだけのPRを自分でマージしてよいという私的な許可がある場合は、それに従う。許可が無いか止められたら、名指しでユーザーに頼む。

上の列挙に当たる判断待ちは、在席ならその場で聞いて決定事項にし、不在・夜間・空席ならaskにする。askは、待たせている人間の条件の束縛に張り（無ければ人間の条件を足して張る。子に束縛した条件には張らない）、待たせるアクティビティをblocksに入れる。orchの説明とログには、判断待ちの中身を書かない。

マージの承認はPRを名指しした形で頼む（見本:「PR AとPR Bをこの順でマージしてよい、と言ってくれれば続けてやる」）。ユーザー自身の文に両方のPR番号が入っていることを確かめる。短い返事で2本目が止められたら、そのPRを名指しして聞き直す。1本ごとにmainへの到達を確かめてから次へ進む。スタックPR（子のbaseが親のブランチ）なら、親をマージした後に子のbaseがmainに切り替わったことを確かめてから子をマージする。

askの回答をマージの承認として別セッションで使うことはしない。マージはorchの窓口で名指しの承認を得てから行う。askの回答後の実行は、そのaskが結びつくorchの担い手が持つ。結びつくorchが空席のときと、orchに結びつかないaskは、トリアージした窓口が実行まで持つ（代わらない）。実行できないなら、ログで手放さず、結びつくorchの預かりに書くか、新しいaskにする。

## やってはいけないこと

- orchの担い手の窓口では、子になる作業をサブエージェントやWorkflowでも回さない。子はbgに振り、bgの中ではサブエージェントを使う（orch自身の判断のための相談役との協議は子の作業ではないので許す。許すのは相談だけで、調査・実測・実装はbgに振る）
- [ユーザーに上げるもの](#ユーザーに上げるもの)の列挙に当たらない判断を、協議と情報収集を経ずにユーザーへ投げない
- bgの中のWorkflowは、ユーザー本人がそのbgに`attach`して自分の言葉で頼んだときだけ使う。依頼文に`"ultracode"`やWorkflowの実行指示を書かない
- ユーザーが子をWorkflowで回したいと言ったときは、その場でどちらの道にするか聞く（子を起票して束縛し、条件のnoteに「orchの窓口で実行中（ユーザー指定）」と書いて自分で実行するか、bgを振ってそこへattachしてもらうか）
- EnterWorktreeは使わない
- マイグレーション番号は、報告先へ宣言してから取る（返事は待たない）
- 人間宛てのaskを、bgに起票させない
- CALM内部の運用裁定の範囲を超えて、既決を見直すことになる判断を自分だけで決めない

## 状態節とgoalの雛形

orchアクティビティの説明の先頭に、次の状態節を置く。上書きで保ち、書くのは記録に無いものだけである。書かないもの: 子の状況（goalにある）、PRの番号と状態（子のgoal・bgの報告・PR本体から引く）、ユーザーの判断待ち（askにする）、他のorchの担当セッション名、運用規約の写し。

```
## 状態
担い手: {名前}（sessionId {sessionId}）／{更新時刻}
（または 担い手: 空席／{更新時刻}）

bg表:
- {子の題} / {bgの短いid} / {作業ツリー} / {起動時刻}

約束:
- {相手のorchアクティビティの題}へ{内容}

預かり:
- {内容}（1件ずつ）

反映待ち:
- {内容}
```

正解の無い仕事（[正解の無い仕事を回す](#正解の無い仕事を回す)）の目的の子には、説明の先頭に次の2節を上書きで置く。

```
## 目的
{誰が、どういう状態か}／1段上の目的／採らなかった読み／やらないこと

## 現在地
いま信じていること／次の一手／やめた手／Claudeが決めたこと（見直す条件つき）／仮置き／現状確認の結果／用語／相談役の所在
```

goalは起点で常設か期限付きかを選ぶ。

- **常設**: 束ねた子の条件と、担い手humanの錠「ユーザーがこのorchを終えることを了承した」を持つ
- **期限付き**: 束ねた子の条件だけを持つ。子が全部済めば判定待ちになる

どちらの形も、最初に振る子を束縛してから書く（束縛条件が無いと空の条件になる）。期限付きでは、振ると分かっている子を振り出す前に全部束縛する。範囲の違う子を後から足してもよい。
