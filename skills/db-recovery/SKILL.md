# db-recovery

SessionStart hookが検知したDBデータ異常減少への自律復旧スキル。検知 → 確認 → 提示 → 承認 → 実行 → 再検証の順で進める。全自動実行はしない。実行前に必ずユーザー承認を取る。

## 発動時の前提

hookの警告は `_build_snapshot_section`(`hooks/session_start_hook.py`)がSessionStartのadditionalContextとして注入する。警告本文には対象テーブルと減少件数(`前回件数 → 現在件数 (-N件)`)が含まれる。このスキルはこの警告文を読み取るところから始まる。

復元本体(`restore_snapshot`)は以下を内蔵している。**このスキルは重複実装しない**:
- 復元前の現行DBの自動退避(`prerestore` スナップショット)
- サーバー稼働中チェック(稼働中は `--force` なしで実行不可)
- スナップショットの整合性検証(`verify_snapshot`)
- schema互換性チェック(巻き戻し疑いは `--yes` なしで実行不可)

## 手順

### 1. 異常確認

- hook警告本文をパースし、どのテーブルが何件減ったか(`discussion_topics` / `decisions` / `discussion_logs` / `activities` / `materials`)を把握する
- 現在のDB状態を実際にクエリして裏取りする(`get_activities` / `get_decisions` 等のcc-memoryツール、または `uv run python scripts/snapshot.py list` で分かる直近の行数)。警告は前回スナップショット取得時点との差分であり、直近の正当な操作(大量retract・tag-cleanup等)による見かけ上の減少でないか確認する
- 確度を判定する:
  - **明確な異常**: 直近セッションで該当テーブルへの意図的な大量削除・retract操作の記憶がない
  - **説明可能**: 直近でtag-cleanup・大量retract等の正当な操作があったことが会話履歴やlogから確認できる
  - **不明**: 判断材料が無い

### 2. スナップショット所在確認

- `uv run python scripts/snapshot.py list`(cc-memoryのインストールディレクトリで実行。プラグイン導入時はプラグインのインストールパス)で全kind横断の一覧を取得する
- 各エントリの `kind` / `created_at` / `db_size_bytes` / `quick_check` を確認する。`quick_check` が `ok` 以外のものは復元候補から除外する
- 異常検知直前(=データがまだ健全だった時点)に最も近いスナップショットを候補として特定する
- 補足: `_build_snapshot_section` は異常検知時(`is_healthy=False`)に新規periodicスナップショットの取得をスキップする実装のため、異常検知セッション中に直前の健全世代が壊れたスナップショットで上書きされることはない

### 3. 復旧方法の提示

ユーザーに以下をA/B/Cの選択肢として提示し、承認を取る。**承認なしに実行しない**。

```
[db-recovery] DBデータ異常減少を検知:
- 対象テーブル: (例: decisions: 1200 → 1050 (-150件))
- 確度: (明確な異常 / 説明可能 / 不明)
- 復元候補: (スナップショットのcreated_at / kind / パス、quick_check結果)

復旧方法を選んでください:
- A: 最新スナップショットから全体復元 — 復元後、復元時点以降に記録した内容は失われる
- B: 部分復元(特定テーブルのみ、または欠落範囲を特定して手動補完)— backup_serviceはテーブル単位・行単位の部分復元を自動化していないため、実質SQLレベルの手動作業になる。工数とリスクを明示した上で提案する
- C: 復旧せず先に進む(誤検知と判断、または復元コストが見合わない場合)
```

- 各選択肢について「何が起きるか」「何を失うリスクがあるか」を必ず併記する
- A/Bは「MCPサーバーの停止が必要」という制約を必ず明示する(`restore_snapshot` は稼働中サーバーに対して `--force` なしでは実行できない)。`--force` / `--yes` を自発的に付けて安全装置を回避しない

### 4. 承認後の実行(Aを選んだ場合)

1. サーバー停止・復元を一連の操作として承認を取る。「復旧していい?」への直接的なyes/noが必要(「任せる」等の一般的信任表明では実行しない)。この承認は停止・復元までを対象とし、再起動は含まない(Step5で復元結果提示後に別途承認を取る)
2. `lsof -ti :52837 -sTCP:LISTEN | xargs kill` でサーバーを停止する(`-sTCP:LISTEN` を外すと :52837 に接続中のブリッジプロセスまで巻き添えでkillされ、生存セッションの再接続競争を誘発する)
3. `uv run python scripts/snapshot.py restore --latest`(Step2で特定した候補が最新でない場合は該当パスを直接指定)を実行する
   - `復元エラー: サーバーが稼働中のため復元を中断しました` が返った場合、Step2が漏れている。サーバー停止を再確認してからリトライする
   - schema互換性警告(`--yes` を要求するメッセージ)が出た場合は、警告文をそのままユーザーに見せて `--yes` 付き再実行の可否を確認する。自己判断で `--yes` を付けない
4. 実行結果(`復元完了: ... -> ...`、行数の変化テーブル、`prerestore_path`)をそのままユーザーに提示する
5. 実行結果の提示後、サーバー再起動(`uv run python -m src.launcher &` 等、`CLAUDE.md` / `CLAUDE.local.md` 記載の手順に従う)について改めてユーザーの明示承認を取る。Step1の一括承認は再起動を含まないため、ここで新たにyes/noを得るまで再起動を実行しない
6. 経緯を `add_logs` で記録する(検知内容・選択した復旧方法・実行結果)

Bを選んだ場合は、対象範囲の特定と手動SQL操作の手順を個別に提示し、実行前に再度承認を取る。

Cを選んだ場合は、誤検知と判断した理由を `add_logs` に記録してスキップする。

### 5. 再検証

- 復元後、主要データが戻っているかを確認する(`get_activities` / `search` 等、または `uv run python scripts/snapshot.py list` で最新スナップショットの行数と突き合わせ)
- 異常が解消していない場合、Step2に戻り別の復元候補(一つ古い世代等)を提案する
- 解消しない場合は「これ以上の自動復旧は困難」と報告し、ユーザー判断に委ねる(無限に世代を遡り続けない。現存する全世代を試して尽きたら停止する)

## Edge Cases

| ケース | 期待挙動 |
|---|---|
| スナップショットが1件もない | 警告のみ提示し、復元不能である旨を伝える。「先に進む」以外の選択肢がないことを明示 |
| 復元に使えるスナップショットが全て `quick_check` 失敗(破損) | 破損している旨を明示し、直近の非破損世代 or 「復元不能」を報告する |
| 復元実行が失敗(`RestoreBlockedError`) | エラーメッセージをそのまま提示し、原因(サーバー稼働中 / 整合性検証失敗 / schema非互換)に応じた対処を提案。無断で `--force` / `--yes` を付けて再実行しない |
| 誤検知(直近の正当な大量retract等が原因と判明) | Cを選択してskipし、判断理由をlogに記録する |
| SessionStart警告以外でDB異常に気づいた場合(会話中に件数の少なさに気づく等) | 同じフローに入ってよい(TRIGGERの2つ目のケース)。Step1で「hook警告なし・自己認識起点」である旨を明記する |
| 復元後も異常が解消しない | Step5の通り別世代を試すか、解消不能として報告する |

## 注意

- 復元前の自動バックアップ(`prerestore` 退避)は `restore_snapshot` が内部で行うため、このスキルが別途手動バックアップを取る必要はない
- MCPサーバーの停止・再起動はユーザー影響が大きい操作。実行前に必ず明示的な承認を取る(一般的な「任せるよ」は承認とみなさない)
- `--force` / `--yes` フラグは安全装置を無効化するものであり、スキル側が自発的に付与しない
- コマンドはcc-memoryのインストールディレクトリ(プラグイン導入時はプラグインのインストールパス)で実行する
