# coding-project-setup

コードプロジェクトの知識フレームをセットアップする。project-setupのsub-skillで、プロファイリング済み（相手はエンジニア・目的は開発）を前提とする。ゴールは「次のセッションがcheck_in・searchで文脈を取れる状態」。既存mdの走査とインタビューは排他ではなく、同一フレームを埋める2つの充填手段。mdで埋まった項目はスキップし、穴だけ聞く。

## フレーム定義（最低限ここまで）

| # | 項目 | 落とし先 |
|---|---|---|
| F1 | プロジェクト識別子＋一言説明 | domain:タグ新設 + notes（リポジトリパス含む） |
| F2 | 関心事の初期素タグ 2〜4個 | 素タグ（固有概念にはdescription付与） |
| F3 | 既に決まっている大方針 | decision（ユーザー裁定を経て記録） |
| F4 | 進行中・直近やること | activity |
| F5 | 参照すべき場所 | domain/素タグのnotesに参照ポインタ |

本skillが設計上あらかじめ落とし先を固定している書き込み（フレームF1〜F5）は、保存先が未確定の依頼を扱う [remember](../remember/SKILL.md) の判定対象ではない。判定が要るのはフレームに収まらない知識のほうで、そちらは後述のとおりrememberの判定木へ流す。

タグは単独で新設できない。domain:タグ・素タグは、それらをtagsに載せたエンティティ書き込みで初めて実体化する。notes・descriptionの付与はその後段でしか行えない。

空のtopicは作らない（議論が始まってから自然発生に任せる）。

## 手順

### Step 1: domain確認
- ユーザーの発話・cwdからdomain名の案を作り、`search_tags`で既存タグとの衝突を確認する
- 既に同名domainのフレームが立っている場合は本skillの対象外。check-inを案内して終了する

### Step 2: md走査（読み取りのみ、何も変更しない）
- 対象: リポジトリ内でremoteから取得できるmd（README / docs/ / CONTRIBUTING / ADR / リポジトリのCLAUDE.md 等）
- 対象外: ユーザーレベルのローカルmd（`~/.claude/`配下等）。CALMの記録はexport等でpeerを超えて人に渡りうるため、取り込み自体を避ける
- フレームF1〜F5への充填案を抽出する。詳細情報は転記・再構造化せず、参照ポインタ（リポジトリ内パス・URL）として扱う

### Step 3: 充填案の提示・裁定
- F1〜F5の充填案と未充填項目を1つの表にまとめて提示する
- 裁定の粒度を分ける: **タグセット（F1/F2）**はまとめて一括承認でよい。**decision候補（F3）**は1件ずつ中身を展開して個別裁定する。md由来の内容はユーザーが裁定して通せば合意扱いとし、sourceに由来mdのパスを明記する
- タグ作成規律: 素タグは少なめに倒す（2〜4個目安）。ディレクトリ構造からの機械的切り出しはしない。description（100字以内の一言定義）を付けるのは「プロジェクト固有の意味・実体を指すタグ」のみ（造語・固有名詞・一般語の固有用法）。一般語彙タグには付けない。判定は「名前が読めるか」ではなく「このプロジェクト固有の意味か」で行う

### Step 4: 未充填分の会話ヒアリング
- フォーム型の質問リストを提示しない。「一言で何？」「N個挙げて」のような要約・圧縮・選別の作業をユーザーに課さない
- 未充填項目を会話の流れに沿って聞く（例: F3が空なら「技術選定とかアーキテクチャでもう決まってることある？」、F4が空なら「直近は何から手をつける？」）
- ユーザーの自由な発話はmdと同じ充填材料として扱い、F1〜F5への構造化（一言説明の起草・タグ候補の抽出）はAIが行って案として提示・裁定を受ける
- 「わからない・まだ無い」は正当な回答。F1のみ必須、F2〜F5は空のまま進めてよい
- フレームに収まらない知識（規範・判断基準・手順・背景の生発話）は [remember](../remember/SKILL.md) の判定木で置き場を判定する

### Step 5: 書き込み実行
- 書き込みは2段構成。タグを実体化させるエンティティ書き込みが先、タグ属性（notes・description）の付与が後になる
  1. セットアップ実行の経緯を`add_logs`で記録する（recording skillの基準に従う）。tagsにはF1のdomain:タグとF2の素タグをすべて載せる。これがタグを実体化させる器を兼ねるので、素タグを載せ忘れると後段のdescription付与が`NOT_FOUND`で落ちる。空のtopicは作らないため`topic_id`は省略する（docstringは必須と書いているが、省略しても動く）
  2. decision（decision-record skillの規律に従う）→ activity（activity-start skillの規律に従う）
  3. タグ属性を`update_tag`で付ける: domain:タグのnotes、固有概念の素タグのdescription、F5の参照ポインタ（domain/素タグのnotesへ）。`update_tag`はnotesとdescriptionを同時指定できず、notesは全文置換なので、domain:タグのnotesは一言説明・リポジトリパス・参照ポインタをまとめた最終形を1回で書く
- mdの全文をmaterialに複製しない

### Step 6: 結果報告
- 作成したフレームの一覧（タグ・decision件数・activity・ポインタ）を提示する

## 運用開始後の増分は対象外

会話中に未知のドメイン固有概念に遭遇したときのインタビューは、habit（未知概念インタビュー）が担う。本skillは初期一括のみ。
