# ask-compose

`add_ask`のquestion/context欄を、概要/背景/選択肢/おすすめの4節構成テンプレートに沿って組み立てる。question/contextの記入品質をここに集約しているため、`add_ask`を呼ぶ前に本スキルの手順を必ず通す。

## 対象

- `add_ask`のquestion/context欄の構成

`add_ask`呼び出し後、レスポンスの`similar_asks`から同型askの反復に気づいたときのメタask起票は`ask-distill` skillが担当する。本スキルはメタask化の判定を行わない。

## テンプレート

questionには「## 概要」を、contextには「## 背景」「## 選択肢」「## おすすめ」を記入する分担を基本とする（questionは500字以内の制約があるため、詳細はcontextに逃がす）。

```markdown
## 概要
- 問題：(何が起きていて、なぜ今判断が要るのかを1-2文で)
- 決めてほしいこと：(Yes/No、またはA/B/Cのどれかを選ぶ、という形に落とし込む)

## 背景
- 今のタスク：(このセッションが何に取り組んでいるか。前提知識ゼロで読める粒度で)
- 経緯：(何をしていてこの分岐に当たったか)
- 影響範囲：(この判断がどこまで効くか。可逆/不可逆をここに含める)
- 放置するとどうなるか：(今のままだと何が止まり続けるか)

## 選択肢
- A: 〜 — メリット：… / デメリット：…
- B: 〜 — メリット：… / デメリット：…

## おすすめ
- 推奨：A
- 理由：(メリデメのどれを重視したか、論拠を明示)

---
一言で答える場合は `A`/`B`/`はい`/`いいえ` だけでもOK
```

## 各項目の記入ガイド

### 概要
- **問題**: 前提を知らない人がこの1-2文だけで「何が起きているか」を理解できるように書く。技術的詳細は背景に譲り、ここでは状況の要約に徹する
- **決めてほしいこと**: 自由記述の問いにしない。人間が数秒で答えられる形（Yes/No、A/B/Cのどれか）に必ず落とし込む。「どう思いますか」のような開いた問いは書かない

### 背景
- **今のタスク**: 読み手がこのセッションの文脈を一切知らない前提で、何に取り組んでいるかを書く
- **経緯**: なぜこの分岐に当たったのか、直前の作業の流れを書く
- **影響範囲**: この判断が及ぶ範囲を書く。特に「後から取り消せるか（可逆）」「一度実行すると戻せないか（不可逆）」を明示する。不可逆な判断ほど詳しい背景が必要になる
- **放置するとどうなるか**: 判断を待たずに放置した場合に何が止まるか、どんな実害が生じるかを書く。緊急度の判断材料になる

### 選択肢
- 最低2案は出す。「やる/やらない」のような単純な二択でも、それぞれのメリット・デメリットは省略しない
- 選択肢の説明は簡潔に。詳細な比較は背景に書き、ここは選ぶための要点だけに絞る
- **選択肢がある場合のみ**、各選択肢のラベル（`- A: 〜 — メリット：…`の`〜`部分。メリット/デメリットの説明文は含めない）を`add_ask`の`choices`引数（`list[str]`）にも渡すことを推奨する。Yes/Noのみで案として列挙するものがないaskでは`choices`を渡さなくてよい（省略時はnull扱い）。ダッシュボード等でのボタン表示に使われるため、Markdown本文のラベルと重複してよい
- `choices`には最大3件・1件100字以内という制約がある。Markdown側の選択肢が4件以上ある場合は、「## おすすめ」に近い優先度上位3件のみを`choices`に渡す（残りはMarkdown本文にのみ残す）。ラベルが100字を超える場合は、100字以内に要約してから渡す（詳細説明はMarkdown側の「## 選択肢」節に残せばよく、`choices`側で削っても情報は失われない）

### おすすめ
- 必ず1案を推奨する。「どちらでもいい」は書かない（推奨が無いと判断委譲の意味が薄れる）
- 理由には、メリット・デメリットのうちどれを重視したかを明示する。「Aがいいと思う」だけでなく、判断の論拠を書く

## 記入例

question:

```markdown
## 概要
- 問題：夜間バッチでの外部API同期中にレート制限（429）を受けた。リトライ待機時間はAPI側の応答で60分と判明している。
- 決めてほしいこと：60分待ってリトライを続行する（A）か、今回は中断し翌日の定期実行に任せる（B）かを選んでほしい。
```

context:

```markdown
## 背景
- 今のタスク：夜間バッチで外部APIから1000件のデータを同期する処理を実行中。
- 経緯：600件処理した時点でレート制限に達した。APIの利用規約上、制限中に再度リクエストを送るとアカウントが一時停止されるリスクがある。
- 影響範囲：可逆。今回のバッチを中断しても、翌日の定期実行で自動的に残り400件を含めて再同期される設計になっている。
- 放置するとどうなるか：判断を待たずに放置すると、バッチプロセスがタイムアウトするまで無応答のまま残り続ける。

## 選択肢
- A: 60分待ってリトライを続行する — メリット：今日中にバッチが完走する / デメリット：セッションを1時間占有し、その間他の処理をブロックする
- B: 今回のバッチは中断し、翌日の定期実行に任せる — メリット：即座にリソースを解放できる / デメリット：今日分のデータ同期が1日遅れる

## おすすめ
- 推奨：B
- 理由：アカウント一時停止のリスクを避けることを最優先した。翌日の定期実行で自動的にリカバリされる設計になっており、1日の遅延は許容範囲と判断した。

---
一言で答える場合は `A`/`B` だけでもOK
```

## ask-distillとの境界

- `ask-compose`（本スキル）: `add_ask`を呼ぶ**前**に、question/contextの構成を担当する
- `ask-distill`: `add_ask`を呼んだ**後**、レスポンスの`similar_asks`を見て同型askの反復に気づいたときのメタask起票を担当する

両者は時系列で別の場面に発動する別スキルであり、混同しない。
