# project-setup

新しいプロジェクト・取り組みの知識フレームをセットアップする。ゴールは「次のセッションがcheck_in・searchで文脈を取れる状態」。最初に相手（ユーザー）を知り、相手に合った充填経路を選ぶ。

## フレーム定義（最低限ここまで）

充填経路によらず共通のゴール。職種中立の語彙で定義する。

| # | 項目 | 落とし先 |
|---|---|---|
| F1 | プロジェクト識別子＋一言説明 | domain:タグ新設 + notes |
| F2 | 主要な関心事 2〜4個 | 素タグ（固有概念にはdescription付与） |
| F3 | 既に決まっている方針 | decision（ユーザー裁定を経て記録） |
| F4 | 進行中・直近やること | activity |
| F5 | 参照すべき場所 | domain/素タグのnotesに参照ポインタ |

本skillが設計上あらかじめ落とし先を固定している書き込み（フレームF1〜F5、およびStep 1のauto-memoryへのペルソナ記録）は、保存先が未確定の依頼を扱う [remember](../remember/SKILL.md) の判定対象ではない。判定が要るのはフレームに収まらない知識のほうで、そちらは後述のとおりrememberの判定木へ流す。

タグは単独で新設できない。domain:タグ・素タグは、それらをtagsに載せたエンティティ書き込みで初めて実体化する。notes・descriptionの付与はその後段でしか行えない。

空のtopicは作らない（議論が始まってから自然発生に任せる）。

## Step 1: プロファイリング

- auto-memoryに既存のユーザーペルソナ（userタイプ）があれば読む。十分ならStep 2へ直行する
- 無い・薄い場合は内部推定する。材料: userレベルの設定（`~/.claude/CLAUDE.md`・rules・導入済みskill/plugin）、作業ディレクトリとホームディレクトリの構成、ここまでの会話の文脈
- 推定するのは「職種・専門性」と「このセットアップの目的」。ユーザーに「あなたはエンジニアですか」と直接は聞かない（内部推定が原則。判定不能なときだけ、目的を普通の言葉で聞く）
- 推定・確認できたペルソナはauto-memoryのユーザーペルソナ（userタイプ）として記録する。既存ペルソナと矛盾したら上書きせずユーザーに確認する
- プロファイリングは取り込みではない: userレベル設定の内容をCALMの記録（decision/material/notes）へ転記しない

## Step 2: 経路選択

- 判定を一言宣言してから進む（例:「コードプロジェクトのセットアップとして進めるね」）。黙って振り分けない。違っていればユーザーがここで訂正できる
- **コードプロジェクト × 開発目的** → [coding-project-setup](../coding-project-setup/SKILL.md) sub-skillへ委譲する（以降の手順はそちら）
- **それ以外** → Step 3（職種中立経路）へ

経路の追加はこのStepの分岐に足す（現時点の分岐はcodingのみ。二分岐固定の設計ではない）。

## Step 3: 職種中立経路（会話ヒアリング）

- フォーム型の質問リストを提示しない。「一言で何？」「N個挙げて」のような要約・圧縮・選別の作業をユーザーに課さない
- オープンな聞き方で始める（例:「このプロジェクトのこと教えて。何をやるやつ？」）。ユーザーの自由な発話を充填材料として扱い、F1〜F5への構造化はAIが行う（coding経路のmd走査と同じ位置づけ）
- 発話から充填案（domain名と一言説明の起草・タグ候補・decision候補）を構成して提示し、裁定を受ける
- 埋まらなかった項目だけ、会話の流れに沿ってフォローアップで聞く（例: F4が空なら「じゃあ最初は何から手をつける？」、F5が空なら「いつも見る場所とか使うツールってある？」）
- 「わからない・まだ無い」は正当な回答。F1のみ必須、F2〜F5は空のまま進めてよい
- タグ作成規律はcoding経路と共通: 素タグは少なめ（2〜4個目安）、description（100字以内の一言定義）を付けるのはプロジェクト固有の意味・実体を指すタグのみ。一般語彙タグには付けない
- フレームに収まらない知識（規範・判断基準・手順・背景の生発話）は [remember](../remember/SKILL.md) の判定木で置き場を判定する（セットアップ独自の仕分けをしない）

## Step 4: 書き込みと報告

- 書き込みは2段構成。タグを実体化させるエンティティ書き込みが先、タグ属性（notes・description）の付与が後になる
  1. セットアップ実行の経緯を`add_logs`で記録する（recording skillの基準に従う）。tagsにはF1のdomain:タグとF2の素タグをすべて載せる。これがタグを実体化させる器を兼ねるので、素タグを載せ忘れると後段のdescription付与が`NOT_FOUND`で落ちる。空のtopicは作らないため`topic_id`は省略する（docstringは必須と書いているが、省略しても動く）
  2. decision（decision-record skillの規律に従う）→ activity（activity-start skillの規律に従う）
  3. タグ属性を`update_tag`で付ける: domain:タグのnotes、固有概念の素タグのdescription、F5の参照ポインタ（domain/素タグのnotesへ）。`update_tag`はnotesとdescriptionを同時指定できず、notesは全文置換なので、domain:タグのnotesは一言説明と参照ポインタをまとめた最終形を1回で書く
- 作成したフレームの一覧（タグ・decision件数・activity・ポインタ）を提示する

## 運用開始後の増分は対象外

会話中に未知のドメイン固有概念に遭遇したときのインタビューは、habit（未知概念インタビュー）が担う。本skillは初期一括のみ。
